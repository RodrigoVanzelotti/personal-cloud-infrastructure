# Releases and recovery

> Read [reconciliation.md](reconciliation.md) first to select the canonical root and owning state. The generic YAML release procedures below do not replace the specialized solution roots.


Source repositories own tests, builds, and publication. For Cloud Run, publish to Artifact Registry and resolve the immutable `@sha256:...` digest. A source-release workflow can use `gh pr create --body-file ...` or a GitHub App to propose a manifest update here. No source repository workflow is changed by this implementation, and automatic cross-repository PR creation is not configured.

For Firebase, publish tested prebuilt static assets under a known directory at an immutable source commit. The infrastructure release job intentionally does not rebuild content. Do not point `public_dir` at private source code or a directory containing credentials. The job checks Firebase's latest live release and skips publication when a retry already has the same infrastructure and source commits. Other releases are published using Firebase CLI. Firebase deploy output and release messages include the source and infrastructure commits; workflow artifacts record success or failure. GitHub artifact retention is finite; retain those records externally if a longer audit history is required. Firebase Hosting's release history remains the authoritative content deployment record. A YAML reference alone does not prove deployment succeeded.

To release:

1. Update the relevant stage YAML's image digest, Hosting commit, or configuration and open a PR. Review validation and the cloud plan.
2. Merge to `main`; enabled staging environments deploy automatically. Check workflow records, Cloud Run readiness, Hosting release history, and the application's smoke checks.
3. Promote by copying the **tested** image digest and Hosting commit into prod YAML in one PR. Grant the production identity access to the same artifacts if they live in another project; do not rebuild them. Registry access for Cloud Run's service agent must be configured explicitly for cross-project images.
4. Merge and have a configured reviewer explicitly approve the production environment deployment. Both production infrastructure and Hosting jobs require their environment approvals; GitHub may request separate approvals for the jobs.

A multi-component or multi-engine release is not atomic. Cloud Run may succeed before Firebase fails, or one Hosting site may fail after another succeeds. Investigate the recorded outcome, fix the cause, and retry the workflow from `main`, or revert the manifest changes together and merge the rollback. Manual workflow dispatch redeploys all components of the selected enabled environment at the selected `main` commit. GitHub may coalesce pending runs in the same concurrency group; the latest queued desired state takes precedence.

To roll back, revert the manifest release references to their previous tested image digest and source commit, open a PR, and use the ordinary deployment/approval path. Preserve old images, static content commits, and secret versions long enough for rollback. Do not use mutable image tags, `latest` secret versions, or moving Git branches. Reverting an image does not roll back a database migration; migrations remain the source application's responsibility and must be backward compatible when needed.

The stack creates Secret Manager **containers**, never versions or values. For a new deployment that needs a secret, first create/import its container with an administrator, add the value outside Terraform, and pin the version before enabling the component. For rotation, add a new version through Secret Manager or `gcloud secrets versions add SECRET --data-file=SECURE_FILE --project=PROJECT`, then update the YAML version through stage and prod. Do not place values in `env`, shell history, `.tfvars`, committed files, or Terraform resources. Keep the old version enabled until all revisions using it are retired and rollback is no longer needed. Cloud Run runtime accounts receive access only to each component's declared secret containers, not individual versions.

For disaster recovery, restore repository access and an administrator's GCP authentication, then inspect the GCS state bucket's object versions. Stop deployments before repairing state. Back up the current state, select the correct historical object generation, restore it using the Cloud Console or documented GCS restore tools, and initialize the exact solution/environment prefix. Run a refresh plan and reconcile it against actual resources before applying. Never restore an older state blindly after resources have changed; importing missing resources is often safer than rolling state back. GCS state locking and object versioning protect concurrent operations and retain historical versions; they do not replace an independent recovery plan for application data.

To retire a resource, use a separately reviewed administrative change and migration plan. Normal deployment jobs reject deletions and replacements. Renaming component keys requires Terraform `moved` blocks or an explicit state migration, not delete-and-recreate. Removing a manifest is rejected by change detection. Disabling an environment pauses management and leaves its resources and state intact; it does not retire them. Do not disable a managed environment as a substitute for resolving a failed plan.
